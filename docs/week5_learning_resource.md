# 5주차 학습자료 — 개인정보를 보호하는 이메일 자동화

## 1. 이번 주차는 어떤 단계인가

5주차는 웹사이트에 있는 정보를 사용자가 직접 찾아오게 하는 단계에서, 동의한 사용자에게 필요한 내용을 자동으로 전달하는 단계이다.

```text
GitHub Actions가 뉴스 수집
  → 일간·주간 이메일 HTML 생성
  → Google Form에서 구독 신청·해지
  → 비공개 Google Sheet에 응답 저장
  → Apps Script가 최신 상태 확인
  → 새 리포트만 이메일 발송
  → 해시 기반 발송 기록으로 중복 차단
```

이 기능의 핵심은 메일을 보내는 코드보다 **동의, 해지, 개인정보와 중복 발송을 안전하게 관리하는 것**이다.

## 2. 꼭 알아야 할 개념

### 옵트인

옵트인은 사용자가 직접 동의하고 구독하는 방식이다. 이메일 주소가 있다는 이유만으로 보내지 않고 다음 조건을 모두 만족해야 한다.

- 요청 유형이 `신규 구독 신청`
- 개인정보 수집 및 이메일 수신에 동의
- 일간 또는 주간 발송 주기를 선택

### 최신 상태 방식

같은 이메일로 여러 번 응답할 수 있으므로 가장 최근 요청을 현재 상태로 사용한다.

```text
신규 신청 → 해지 요청       = 해지 상태
신규 신청 → 해지 → 다시 신청 = 구독 상태
```

과거 행을 삭제하지 않아도 변경 과정을 남기면서 현재 상태를 판단할 수 있다.

### Google Form 섹션 분기

신규 신청자는 관심 직무·기업·발송 주기와 동의를 입력해야 하지만, 해지 요청자에게 같은 내용을 다시 묻는 것은 불필요하다.

- 첫 화면: 이메일 주소, 요청 유형
- 신규 신청: 관심 항목, 발송 주기, 수신 동의
- 해지 요청: 추가 질문 없이 제출

이처럼 답변에 따라 다른 섹션으로 보내는 기능이 섹션 분기이다.

### 미리보기와 실제 응답 링크

Google Forms의 미리보기 모드는 화면 구성을 확인하는 용도라 제출 버튼이 비활성화될 수 있다. 실제 시험은 공개 응답용 링크에서 해야 한다. `진행상황이 복원되었습니다`는 오류가 아니라 브라우저가 작성 중이던 답을 불러온 것이며, `양식 지우기`로 초기화할 수 있다.

### Apps Script

Apps Script는 Google Sheet를 읽고 이메일을 보내거나 정해진 시간에 함수를 실행할 수 있는 Google의 자동화 도구이다.

이 프로젝트의 주요 함수는 다음과 같다.

| 함수 | 역할 |
| --- | --- |
| `previewDeliveryPlan` | 메일을 보내지 않고 승인·중복·발송 예정 인원만 계산 |
| `sendTestToLatestSubscriber` | 가장 최근 유효 신청자 1명에게 시험 메일 발송 |
| `sendDailyDigest` | 일간 신청자에게 새 일간 리포트 발송 |
| `sendWeeklyDigest` | 주간 신청자에게 새 주간 리포트 발송 |

### 트리거

트리거는 정해진 시간에 함수를 자동으로 실행하는 예약 장치이다.

- 매일 오전 7시경: GitHub Actions가 뉴스 수집과 이메일 파일 생성
- 매일 오전 8~9시: 일간 메일 확인·발송
- 매주 월요일 오전 9~10시: 주간 메일 확인·발송

Apps Script의 시간 기반 트리거는 정확히 정각이 아니라 선택한 1시간 범위 안에서 실행될 수 있다.

### 해시

해시는 이메일을 일정한 길이의 알아볼 수 없는 값으로 바꾸는 방법이다. 같은 이메일은 같은 해시가 나오므로 발송 이력을 비교할 수 있지만 발송 기록만 보고 원래 이메일을 쉽게 알 수 없다.

```text
이메일 원문 → SHA-256 → 구독자 키
```

실제 이메일 주소는 비공개 응답 시트에만 있고, 발송 기록에는 해시값을 남긴다. GitHub에는 구독자 정보를 올리지 않는다.

### 중복 방지

중복 방지 키는 다음 세 값을 합쳐 만든다.

```text
구독자 해시 + 발송 주기 + 콘텐츠 해시
```

이미 `성공` 기록이 있는 조합은 다시 발송하지 않는다. 실제 검사에서 주간 승인 1명, 중복 제외 1명, 발송 예정 0명이 확인되었다.

### 안전 잠금과 발송 한도

- `LIVE_SEND_ENABLED = false`: 실제 다중 발송을 막는 비상 잠금
- 스크립트 잠금: 동시에 두 발송이 실행되는 것을 차단
- 1회 최대 20명: 실수로 많은 메일이 발송되는 위험을 제한
- Google 남은 일일 한도 확인: 계정 한도를 넘지 않도록 제한
- 새 기사 없음: 발송하지 않음

## 3. 문제와 해결 과정

### 해지할 때도 모든 질문을 요구함

원인: 모든 질문이 한 흐름에 있고 필수로 설정됨.

해결: 요청 유형을 기준으로 신규 신청과 해지 섹션을 분리하였다.

### 제출 버튼이 비활성화됨

원인: 실제 응답 링크가 아니라 미리보기 모드에서 시험함.

해결: 공개 응답용 링크에서 다시 시험하였다.

### 다시 신청할 때 이전 상태가 나타남

원인: Google Forms가 작성 진행상황을 브라우저에 저장함.

해결: `양식 지우기` 후 다시 신청하였다.

### 실수로 여러 사람에게 보낼 위험

해결: 대상 미리보기 → 본인 1명 시험 → 실제 1건 → 중복 확인 순서로 범위를 넓혔다. 다중 발송은 별도 잠금값을 true로 변경한 뒤에만 가능하도록 했다.

## 4. AI가 한 일과 내가 한 일

### AI가 도운 부분

- Google Form과 Apps Script 구성 방법 안내
- 최신 상태 판별, 해시 기록과 중복 방지 코드 작성
- 오류 화면의 원인 설명
- 개인정보 보호와 안전장치 점검 목록 작성

### 내가 판단하고 확인한 부분

- 구독 폼에 필요한 질문과 동의 문구 결정
- 해지 사용 경험이 불편하다는 문제 발견
- 실제 응답과 비공개 Sheet 저장 확인
- 시험 메일과 실제 1건 수신 확인
- 중복 제외 결과 확인
- 일간·주간 발송 시간 결정과 트리거 등록

AI가 코드를 작성했더라도 실제 개인정보와 이메일 발송에 영향을 주는 단계는 사용자가 직접 확인하고 승인하였다.

## 5. 직접 설명해 볼 문장

> 구독자 정보는 비공개 Google Sheet에만 저장하고 공개 GitHub에는 넣지 않았다. Apps Script는 이메일별 가장 최근 신청·해지 상태와 수신 동의를 확인하고, 같은 콘텐츠의 성공 기록이 있으면 발송을 건너뛴다. 전체 발송 전에 대상 확인, 본인 시험, 실제 1건, 중복 차단 순서로 검증하였다.

## 6. 복습 실습

1. 신청 → 해지 → 재신청 순서일 때 최종 상태가 무엇인지 말한다.
2. `previewDeliveryPlan`과 `sendWeeklyDigest`의 차이를 설명한다.
3. 발송 기록 시트에 이메일 원문이 없는지 확인한다.
4. 같은 주간 리포트를 두 번 보내지 않는 기준을 말한다.
5. GitHub 뉴스 수집과 Apps Script 메일 발송 시간의 순서를 설명한다.
6. `LIVE_SEND_ENABLED`를 false로 두면 어떤 일이 일어나는지 설명한다.

## 7. 운영할 때 확인할 사항

- GitHub Actions의 매일 수집 작업이 성공했는가?
- Apps Script 트리거의 최근 실행과 오류율이 정상인가?
- 새 기사가 없는 날 발송되지 않았는가?
- 해지 요청자가 이후 발송 대상에서 제외되었는가?
- 발송 기록에 이메일 원문이 저장되지 않았는가?
- 실패 메일이 반복해서 재시도되고 있지 않은가?

## 8. 자가점검

- 옵트인과 최신 상태 방식의 의미를 설명할 수 있는가?
- Form, Sheet와 Apps Script의 역할 차이를 알고 있는가?
- 해시와 암호화가 완전히 같은 개념이 아님을 알고 있는가?
- 중복 발송 방지 키의 세 요소를 말할 수 있는가?
- 실제 자동 발송 전에 단계적으로 시험한 이유를 설명할 수 있는가?

다섯 질문에 답할 수 있으면 5주차 이메일 자동화의 핵심 구조를 이해한 것이다.
