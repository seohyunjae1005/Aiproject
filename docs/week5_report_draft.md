# 5주차 주차보고서 초안

> 실제 활동일시와 인증사진은 본인의 기록에 맞게 입력한다. 아래 내용 중 직접 확인하지 않은 사항이 있다면 제출 전에 삭제하거나 수정한다.

## 활동일시

- 활동일: `[실제 날짜 입력]`
- 실제 시작 시각: `[직접 입력]`
- 실제 종료 시각: `[직접 입력]`
- 실제 활동시간: `[직접 계산]`

## 활동 목표

반도체 기업의 새 공식 기사와 공정·양산기술 중심 리포트를 희망자에게 안전하게 전달하는 이메일 구독 기능을 완성한다. 구독 신청과 해지를 구분하고, 개인정보를 공개 저장소와 분리하며, 새 기사가 없거나 이미 보낸 리포트는 발송하지 않는 자동화 구조를 구축한다.

## 수행내용

최근 1일과 7일 기사를 이메일 형태의 HTML로 생성하고, 한국어 제목·요약, 회사, 게시일, 기술 분야, 관련 직무, 공식 원문 링크와 월간 공정 직무 리포트를 포함하였다. 실제 구독자 정보를 사용하기 전 개인정보와 추적 픽셀이 없는 미리보기 파일을 GitHub Actions에서 생성하였고, 최근 7일 기사 5건이 포함된 결과를 직접 내려받아 내용과 링크를 확인하였다.

Google Form에는 이메일 주소, 관심 직무, 관심 기업군, 희망 발송 주기, 개인정보 수집 및 이메일 수신 동의, 요청 유형을 구성하고 응답을 비공개 Google Sheet에 연결하였다. 처음에는 해지 요청자도 관심 직무·기업·발송 주기와 동의를 다시 선택해야 하는 문제가 있었다. 직접 해지 과정을 시험하면서 불편을 발견한 뒤 첫 화면에서는 이메일과 요청 유형만 받고, 신규 신청은 상세 질문 섹션으로, 해지는 바로 제출 섹션으로 이동하도록 답변 분기를 적용하였다. 미리보기 모드에서는 제출 버튼이 비활성화되고 이전 진행상황이 복원되는 현상도 확인하여 실제 응답 링크와 양식 초기화 방법을 구분하였다.

Google Sheet에 연결한 Apps Script는 같은 이메일의 가장 최근 신청·해지 요청을 현재 상태로 판단하고, 신규 구독 신청과 수신 동의를 모두 만족한 사용자만 대상으로 삼도록 구성하였다. 일간과 주간 신청자를 분리하고, 발송 전에는 실제 메일 없이 승인·중복·발송 예정 인원만 계산하였다. 본인 이메일 1건으로 시험 메일과 실제 주간 메일을 차례로 확인하였다. 발송 기록에는 이메일 원문 대신 SHA-256 해시를 저장하고 `구독자 해시·발송 주기·콘텐츠 해시` 조합을 비교하도록 하였다. 같은 리포트를 다시 검사한 결과 `승인 1명·중복 제외 1명·발송 예정 0명`으로 표시되어 중복 방지가 정상임을 확인하였다.

실수로 많은 메일이 발송되지 않도록 실제 다중 발송 잠금, 동시에 실행되는 작업 차단, 1회 최대 20명 제한과 Google 계정의 남은 발송 한도 확인을 추가하였다. 새 기사가 없는 일간 리포트는 발송 계획 없음으로 처리되었다. 마지막으로 뉴스 수집이 끝난 뒤 실행되도록 일간 메일은 오전 8~9시, 주간 메일은 월요일 오전 9~10시의 시간 기반 트리거를 등록하였다.

## 문제 상황과 개선 과정

### 1. 해지 과정의 불필요한 필수 입력

모든 질문을 필수로 설정하자 해지 요청자도 관심 항목과 수신 동의를 다시 입력해야 했다. 요청 유형 질문을 기준으로 섹션을 나누어 해지자는 이메일과 해지 요청만 제출하도록 수정하였다.

### 2. 제출 버튼 비활성화와 진행상황 복원

Google Forms의 미리보기 화면은 제출용 화면이 아니어서 버튼이 비활성화되었다. 공개 응답 링크에서 다시 시험하고, 이전 입력이 복원될 때는 양식 지우기로 초기화하였다.

### 3. 중복 및 대량 발송 위험

처음부터 전체 발송을 설정하지 않고 발송 예정 인원 확인, 본인 시험 메일, 실제 1건 발송, 같은 콘텐츠 재검사의 순서로 범위를 넓혔다. 발송 성공 기록과 콘텐츠 해시를 비교하고 다중 발송 잠금 및 최대 인원 제한도 추가하였다.

### 4. 개인정보 공개 위험

구독자 이메일은 비공개 Google Sheet에만 저장하고 GitHub 저장소에는 넣지 않았다. 발송 기록에도 이메일 원문 대신 해시값을 남기도록 결정하였다.

## 성찰내용

이번 활동을 통해 이메일 자동화는 메일을 보내는 코드만 구현하면 끝나는 일이 아니라 동의, 해지, 개인정보, 중복 발송, 계정 한도와 실패 상황을 함께 관리해야 하는 작업임을 배웠다. 특히 해지 과정을 직접 사용해 보지 않았다면 사용자가 모든 관심 항목을 다시 선택해야 하는 불편을 발견하지 못했을 것이다. 이를 통해 프로그램이 작동하는지만 확인하지 않고 사용자의 입장에서 전체 흐름을 시험하는 것이 중요하다고 느꼈다.

또한 AI가 만든 코드를 곧바로 여러 사람에게 적용하지 않고, 발송 대상 수만 확인한 뒤 본인 1명에게 시험하고 실제 발송과 중복 방지를 차례로 검증하였다. 나는 코드를 처음부터 혼자 작성하지는 않았지만 어떤 정보가 공개되면 안 되는지, 어느 단계에서 발송을 잠가야 하는지, 어떤 결과가 성공을 의미하는지를 결정하고 직접 확인하였다. 이 경험을 통해 AI 활용 능력은 답을 복사하는 것이 아니라 위험을 예상하고 검증 범위를 조금씩 넓히며 결과에 책임지는 과정이라는 점을 이해하였다. 앞으로도 자동 실행 기록과 오류율을 정기적으로 확인하고, 새로운 기능을 추가하기 전에 개인정보와 사용자에게 미치는 영향을 먼저 점검하고자 한다.

## 활동 결과

- 일간·주간 이메일 HTML 자동 생성
- Google Form 신규 신청·해지 분기와 비공개 Sheet 연결
- 최근 요청 기준 구독 상태와 수신 동의 판별
- 본인 이메일 시험 발송 및 실제 주간 메일 1건 발송 성공
- 이메일 해시 기반 발송 기록과 동일 콘텐츠 중복 차단 검증
- 새 기사 없는 날 발송 생략
- 동시 실행 잠금, 1회 최대 20명과 계정 발송 한도 적용
- 일간·주간 시간 기반 자동 발송 트리거 등록

## 다음 활동 계획

실제 사용자의 의견을 받아 이메일과 웹사이트의 모바일 가독성을 개선한다. GitHub Actions와 Apps Script의 자동 실행 성공률, 발송 오류와 구독 해지 반영 여부를 정기적으로 확인한다. 수작업으로 기업 뉴스를 찾을 때와 자동화 이후의 탐색 시간을 같은 조건에서 측정하여 프로젝트 효과를 정량적으로 비교한다.
